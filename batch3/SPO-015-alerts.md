# SharePoint Alerts Not Sending

**Category:** SharePoint > Alerts
**Article Code:** SPO-015
**Tier:** 2
**Audience:** Administrators / Technicians
**Estimated Resolution Time:** 30–90 minutes (longer if the root cause is Exchange mail flow or a service-side incident)

> **Retirement notice (read first):** Microsoft began removing classic SharePoint Alerts starting **July 2026**. Alerts may stop functioning entirely on tenants where the retirement has rolled out, regardless of configuration. Before spending time troubleshooting, confirm the tenant still supports alerts and set customer expectations. The durable replacement is a **rule** (list/library **Automate > Rules**) or a **Power Automate** flow. See the Prevention section. Reference: https://aka.ms/retirement/alerts/support

Classic SharePoint Online alerts email a user when items in a list or library are added, changed, or deleted. When they stop arriving, the cause is almost always one of: the user profile has no email address, the user lost permission to the object, alerts are disabled at the tenant, throttling, the target is an unsupported group type, or an Exchange/service-side mail issue. This article works those causes in order.

## Symptoms / When to Use

- A user created an alert on a list, library, or document but never receives notification email after an item is added, edited, or deleted.
- On creating an alert the user sees: *"You do not have an e-mail address. Alert has been created successfully but you will not receive notifications until valid e-mail or mobile address has been provided in your profile."*
- Existing alerts stopped arriving even though new alerts on a test library work.
- No alerts arrive for **any** user across multiple sites (points to tenant-wide disable or a service incident).
- Alerts sent to a distribution list or Microsoft 365 Group are silently not delivered.
- Task-list or workflow notification emails also fail (shared root cause: outgoing mail).

## Background

SharePoint Online alerts are generated by the alert subscription engine and delivered as email through Exchange Online. Delivery depends on a chain that must be intact end to end:

1. The subscribing user has a **valid work email** on their SharePoint user profile. This is normally populated from the mailbox; users **without an Exchange Online license** frequently have a blank profile email, which silently breaks delivery.
2. The user holds at least **Read** permission on the target list/library. Alerts respect item security; losing access silently stops the alert.
3. Alerts are **not disabled at the tenant**. `Set-SPOTenant -StopAlerts $true` turns alerts off for the entire organization.
4. The recipient is a **user or a mail-enabled security group**. Alerts to distribution lists and Microsoft 365 Groups are **not supported** and will not deliver.
5. Exchange Online accepts and delivers the message (not blocked by junk filtering, connectors, or a service incident), and the send is not being **throttled** for excessive immediate-alert volume.

Because the failure is silent at several links, work the chain top-down rather than guessing.

## Resolution

### Step 1: Confirm the user profile has a work email

This is the most common cause, especially for shared, service, or unlicensed accounts. As a SharePoint administrator:

1. Go to the SharePoint admin center (`https://<tenant>-admin.sharepoint.com`) **> More features > User profiles > Open**.
2. Select **Manage User Profiles**, search the affected user, and confirm **Work email** is populated with a valid, mail-enabled address.

If the field is blank, allow users to edit and replicate the property:

1. In **User profiles**, under **People**, select **Manage User Properties**.
2. Locate **Work email**, hover, open the drop-down, and select **Edit**.
3. Under **Edit Settings**, enable **Allow users to edit values for this property**.
4. Under **Policy Settings**, select **Replicable** (required so the value propagates to all site collections), then **OK**.

The most reliable long-term fix is assigning the account an **Exchange Online license** so the profile email populates automatically.

### Step 2: Verify the subscriber's permissions

Confirm the user has at least **Read** on the target object. Alerts fire only for items the subscriber can see.

1. On the list/library, open **Settings (gear) > Library/List settings > Permissions for this ... library**.
2. Confirm the user (directly or via a group) has a permission level of Read or higher.

If permissions are missing, grant access, then have the user delete and recreate the alert.

### Step 3: Confirm alerts are not disabled tenant-wide

If **no** user receives alerts anywhere, check the tenant `StopAlerts` flag. Connect with the SharePoint Online Management Shell:

```powershell
Connect-SPOService -Url https://<tenant>-admin.sharepoint.com
Get-SPOTenant | Select-Object StopAlerts
```

If `StopAlerts` is `True`, re-enable alerts:

```powershell
Set-SPOTenant -StopAlerts $false
```

`Set-SPOTenant` requires SharePoint administrator rights and the `Microsoft.Online.SharePoint.PowerShell` module. Reference: https://learn.microsoft.com/powershell/module/microsoft.online.sharepoint.powershell/set-spotenant

### Step 4: Test with a fresh alert

Isolate old-vs-new alert behavior. On a **test library**:

1. Have the user select **... > Alert me** (or **Automate > Alert me**) and create an immediate email alert.
2. Add, edit, or delete an item to trigger it.
3. Wait up to **15 minutes** — alerts are not instantaneous.

If the new alert arrives but old ones do not, the user's existing subscriptions are stale — proceed to Step 5. If even the new test alert fails after Step 1–3 are clean, escalate to Step-level troubleshooting below (Exchange/service).

### Step 5: Delete and recreate stale alerts

Corrupt or orphaned subscriptions are cleared by removing and recreating them.

- **End user:** on the site, **Settings (gear) > Alert me / Manage my alerts**, delete all listed alerts, then recreate the needed ones.
- **Site admin:** **Settings (gear) > Site settings > Site Administration > User alerts**. Select the affected **Display alerts for** user and **Delete Selected Alerts**. The user then recreates them.

## Troubleshooting

If alerts still fail after the main path, check these variations:

- **Unsupported recipient type.** Alerts cannot be delivered to **distribution lists** or **Microsoft 365 Groups**. Only individual users and **mail-enabled security groups** are supported. Re-point the alert to a supported recipient.
- **Throttling on high-volume immediate alerts.** If one address receives several thousand immediate alerts per hour across all subscriptions, SharePoint throttles delivery to protect service health. Switch heavy subscriptions from **immediate** to a **daily/weekly summary**, or consolidate them.
- **Junk/quarantine.** Confirm the alert mail is not landing in the user's **Junk Email** folder or Exchange **quarantine**. Add the SharePoint sender to allowed senders if needed.
- **Exchange mail flow.** If no SharePoint email of any kind is arriving, test general mail flow to the same mailbox. If ordinary email is also delayed or missing, the fault is Exchange, not SharePoint — investigate connectors, transport rules, and message trace in the Exchange admin center.
- **Service incident.** In the Microsoft 365 admin center, check **Health > Service health** for active SharePoint or Exchange advisories before deeper troubleshooting. A tenant-wide, all-user failure with clean configuration is frequently a service-side issue or the alerts retirement rollout.
- **Custom email content expected.** Native alerts cannot use custom templates. If the customer needs branded or conditional notifications, that requires Power Automate or SharePoint Designer workflows — it is not an alert bug.

If Steps 1–5 are clean and a fresh test alert still fails on a non-retired tenant, collect the last known good time and exact reproduction steps, then open a Microsoft support case.

## Prevention

- **Migrate off classic alerts.** With retirement underway (July 2026), move business-critical notifications to **list/library Rules** (**Automate > Manage rules**) for simple add/change conditions, or **Power Automate** flows (**Automate > Power Automate**, or a scheduled reminder flow on a date column) for anything richer. These are the supported forward path.
- **License mailboxes that need alerts.** Ensure any account expected to receive notifications has an Exchange Online license so its profile email stays populated.
- **Use supported recipients.** Target individual users or mail-enabled security groups; never distribution lists or Microsoft 365 Groups.
- **Prefer summary over immediate** for high-churn lists to avoid throttling.
- **Document alert ownership** so that when staff change roles or lose object permissions, their alerts are reviewed and reassigned rather than silently failing.
- **Baseline mail flow.** Keep Exchange Online mail flow and anti-spam allow-lists healthy; most "SharePoint alert" failures are actually email delivery failures.
